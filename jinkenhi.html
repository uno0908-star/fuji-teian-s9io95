01なぜ平均±標準偏差ではなく、中央値とMADなのか

異常検知の基準を平均と標準偏差で作ると、異常値そのものが基準を汚します。人件費率が突出した事業所が数件あるだけで平均も標準偏差も引き上げられ、その事業所が「平均から2σ以内」に収まってしまう。セグメントあたり20〜60事業所という規模では、これが現実に起きます。

そこで中央値と MAD（中央絶対偏差）を使います。半数が外れ値にならない限り基準が壊れません。正規分布のとき標準偏差と一致するよう 1.4826 を掛けて、見慣れたZスコアと同じ感覚で読める形にします。

MAD = median( | xi − median(x) | )
ロバストZ = ( x − median(x) ) ÷ ( 1.4826 × MAD )
x ＝ 当該事業所の人件費率、median/MAD ＝ 同一サービス種別 × 同規模帯のセグメント内で算出

そのうえで、Zスコアだけに頼りません。「水準は高くないが、先月から急に悪化した」事業所はZでは拾えないので、前月比・過去12か月の自己水準からの乖離を別ルールとして並列に回し、どのルールで引っかかったかを一覧に出します。ルールを1本に統合しないのは、あとから「なぜこの事業所が出たのか」を説明できるようにするためです。

02原因分解——ここがこの仕組みの中心だと考えています

「人件費が増えた」という事実から先に進むには、増えた金額を互いに重ならない要因に分けきる必要があります。人件費を次のように置くと、増減を分解できます。

人件費 = ( 総実働時間 H × 平均時間単価 w ) + 諸手当 + 賞与・一時金 + 法定福利費

Δ人件費 = ΔH × w0  +  Δw × H1  +  Δ諸手当  +  Δ賞与  +  Δ法定福利費
　　　　　　　数量効果　　　　単価効果　　　　　　　　　　　　　　（添字0＝比較期間、1＝当月）

ΔH = Δ所定内 + Δ残業 + Δ休日勤務 + Δ応援受入 − Δ応援送出
Δw = 職種構成の変化 + 昇給・処遇改善 + 高単価職員の勤務比率

この形にしておくと、画面のウォーターフォールがそのまま説明文になります。「時間が増えたのか、単価が上がったのか、一時金が乗ったのか」は打つ手がまったく違うので、ここを混ぜたまま出すと現場は動けません。賞与・一時金を除いた経常ベースを必ず併記するのも同じ理由です。処遇改善加算の一時金支給月は人件費率が跳ねますが、それは異常ではありません。

03LLMに何をさせて、何をさせないか

数値の判定はPython側で完結させ、LLMには「確定した数値を、人が読んで動ける文章に組み立てる」役割だけを与えます。理由は3つあります。再現性（同じ入力で同じ判定が出ないと監査に使えない）、検証可能性（なぜその事業所が出たのかを式で説明できる）、そしてコストです。

工程担当理由
取込・名寄せ・突合Python / pandas再現性が要る。毎月同じ結果になる必要がある
異常スコアの算出Python式で説明でき、検算できる
原因の金額分解Python合計が必ず一致する（分解の残差ゼロ）ことを担保
確認事項の抽出Python + ルール「影響額上位3名」等は計算で決まる
文章化・優先順位の言語化LLM APIここだけは人が読む文章にする価値がある

個人情報をAPIに送らない設計にします。LLMへ渡すのは集計済みの数値と、事業所内で採番した職員ID（E-0417 等）だけです。氏名・生年月日・住所・賃金台帳の原本は送りません。出力を画面に表示する際に、手元の対応表でIDを氏名に戻します。既存のクラウド契約に合わせて Amazon Bedrock / Google Vertex AI 経由にすることもできます。

04500事業所に、個別ルールを作らないための設計

いちばん重要な制約だと考えています。個別作り込みを避ける鍵は2つです。

ひとつは、事業所ごとの違いをコードではなく「表」に追い出すこと。判定の基準値はコードに書かず、セグメント（サービス種別 × 規模帯）ごとのパラメータ表として持ちます。事業所が増えてもコードは1行も増えず、セグメントに割り当てるだけです。サンプルが少ないセグメント（n<15）は自動的に上位区分へマージして、統計が暴れないようにします。

もうひとつは、取込の様式差を「列名マッピング定義」で吸収すること。事業所ごとにExcelの列名や並びが違うのは避けられませんが、そのたびに読込コードを書き足すと保守が破綻します。「この様式では『実働時間』が『総労働時間』という列名で7列目にある」という対応表を定義ファイルとして持ち、コードは定義に従って読むだけにします。新しい様式が出てきたときに追加するのは定義の1ブロックであって、プログラムではありません。

WEEK 1

WEEK 3

WEEK 4

WEEK 5
全事業所への展開
500事業所分のバッチ実行、LLM連携、Excel出力。処理時間とコストを実測します。

しきい値の調整、ソースコードと手順書。社内で運用・改修できる状態にします。

週1回の定例は、上の各週の終わりに置く想定です。Week 3 の「実感と合うか」の確認が、一番重要な工程だと考えています。ここで感触が合わなければ、判定の軸そのものを組み替えます。

06先に申し上げておきたい前提とリスク

  • データ形式のばらつきが最大の工数変動要因です。500事業所が同一様式なら取込は数日ですが、法人ごとにバラバラだと定義作りに時間がかかります。サンプルを拝見してから実装範囲を合意させてください。
  • 応援勤務の計上ルールを最初に確認させてください。応援元・応援先のどちらで人件費を計上する運用かで、分解の式が変わります。ルールが統一されていない場合は、その不整合の検出自体を成果物に含めます。
  • PLと賃金台帳が突合しない事業所は、分析より先に原因を潰す必要があります。合計が合わないデータから出した異常値は信用できません。突合結果を毎月レポートに出す設計にしています。
  • 賞与月・処遇改善加算の一時金支給月は、そのままだと全事業所が異常判定になります。経常ベースの併算と、支給月マスタでの補正を最初から入れます。
  • このデモには実装していないもの：実データの取込、認証・権限、実際のAPI呼び出し、データベース。この画面はブラウザだけで完結するダミーです。
